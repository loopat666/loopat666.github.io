ADT MCP + Claude Code 바이브 코딩 절차

S/4HANA 2023 온프레미스 개발서버에 ADT for VS Code를 연결하고, 내장 ADT MCP 서버를 Claude Code에 붙여 CDS를 읽고, 만들고, 고치는 데까지 한 번에 정리했다. 형이 설계·승인하고 Claude Code가 구현하는 구조다.

개요

  • 목표는 반복 작업을 Claude Code에 맡기는 연습이다. 설계와 승인은 형이 하고, 구현은 Claude Code가 한다.
  • 연결 고리는 VS Code의 ADT 확장이 띄우는 MCP 서버(localhost:2236)다. Claude Code가 이 서버의 툴 34개를 쓴다.
  • 오늘의 순서는 연결 → MCP 켜기 → 등록 → 안전장치 → 읽기 → 신규 생성 → 기존 수정이다.
  • S/4HANA 2023 연결은 실제로 성공했다(관찰). SAP 튜토리얼의 전제 버전은 2025 이상이라 공식 지원 여부는 확인하지 못했다.

1

ADT for VS Code 연결

  • 온프레미스는 RFC destination을 쓴다. SAP Logon 구성이 전제다.
  • 예전 ABAP FS 폴더와 섞이지 않게 새 폴더를 쓰고, 그 워크스페이스에서는 ABAP FS 확장을 비활성화했다.
  • 폴더에 "Disconnected … abap:/repotree-v1/…" 경고가 뜨면 destination의 로그온 정보(비밀번호)를 입력해야 연결된다.
  • 처음 증상의 원인이 ABAP FS 충돌인지 로그온 미입력인지는 분리해서 확인하지 못했다.
  • 이 파일에는 서버 주소와 사용자 ID가 들어 있다. 채팅 입력창에 자동 첨부되면 칩을 지우고, git에는 올리지 않는다.
2

ADT MCP 서버 켜기

  • 설정에서 adt.mcpServer.enabled를 켠다(검색어 adt mcp). 포트는 2236, 엔드포인트는 http://localhost:2236/mcp다.
  • 서버는 시작할 때마다 bearer 토큰을 새로 만든다. 서버를 껐다 켜면 토큰이 바뀐다.
  • Access Restrictions의 패키지 제한은 생성·수정에만 적용되고 읽기에는 적용되지 않는다. 그래서 읽기 범위는 CLAUDE.md로 따로 제한한다.
  • VS Code MCP 로그에 "Connection state: Running"과 "Discovered 33 tools"가 보이면 정상이다.
3

Claude Code에 등록

  • 토큰은 파일이나 프롬프트에 넣지 않고 환경변수로만 다룬다. 길이가 22인지 확인한 뒤 등록한다.
  • --scope user로 등록해야 VS Code 확장 세션에서 보였다. local scope로 등록했을 때는 패널과 세션에 adt가 안 보였다(원인은 작업 경로 불일치로 추정, 미검증).
  • 서버를 재시작하면 토큰이 바뀌므로 claude mcp list가 Connected인지 먼저 보고, 끊겼을 때만 다시 등록한다.
4

안전장치 설정

  • CLAUDE.md는 어기면 막을 장치가 없다. 그래서 .claude/settings.json으로 쓰기 툴은 매번 승인(ask), 위험 툴은 차단(deny)한다.
  • Edit File Tool 설정이 꺼져 있었는데도 abap_object_edit_file이 실제로 동작했다. 지금 쓰기를 막는 장치는 ask 규칙이다.
  • 저장 후 /permissions에서 "From shared project settings"로 ASK 6개, DENY 4개가 보이면 적용된 것이다.
  • 승인 창은 "allow once"로만 누른다. "always allow"는 누르지 않는다.
5

읽기 시험

  • 검색·읽기 툴은 destination이 필수다. 모르면 추측하지 말고 abap_destination_list를 한 번 허용해서 목록을 받는다.
  • 목록이 두 개(_ABAP, _ADT)로 나와서 Claude가 멈추고 물었다. 형이 _ADT를 골랐다.
  • 결과로 ZR_YHL2609_00005의 구조와 확인할 점 4가지를 요약받았다. 쓰기 툴은 쓰지 않았다.
  • destinations.json에서 _ABAP를 지운 뒤에도 목록이 두 개로 나왔다. 서버가 시작 시점의 목록을 들고 있는 것으로 의심하지만 확인하지 못했다.
6

쓰기 1: CDS 신규 생성

  • 새 오브젝트라 기존 소스를 건드리지 않는 안전한 첫 쓰기다. 순서는 계획 → validate → create → 템플릿 읽기 → edit_file → check → activate다.
  • 필드명은 추측하지 않고 SPFLI 테이블 정의를 읽어서 정했다. distance는 단위 필드(distid)와 연결하는 annotation을 붙였다.
  • create 직후에는 필드명을 CamelCase로 바꾼 기본 템플릿이 생긴다. 확정 소스로 바꾸는 diff를 승인한 뒤 edit_file을 실행했다.
  • 모든 쓰기 단계에서 승인 창이 떴고, activate는 따로 승인했다. 이클립스에서 생성 결과도 직접 확인했다.

7

쓰기 2: 기존 소스 수정

  • 필드 한 줄 수정은 계획 단계를 건너뛰었다. 대신 현재 소스 읽기 → 새 이름으로 백업 → diff 표시 → edit_file → 재읽기 비교 → check를 한 프롬프트에 묶고, activate는 따로 승인했다.
  • 백업 파일은 before2처럼 다른 이름으로 남긴다. 기존 파일을 덮어쓰지 않는다는 규칙 때문이다.
  • 결과는 16번째 줄 한 줄만 바뀌었고, check와 activate 모두 통과했다. 이력은 docs/history/2026-11-17_ZR_YHL2609_00030_04_수정.md에 남았다.
  • 검증 필요: fltime이 원래 INT4라면 이 cast는 실제로 아무것도 바꾸지 않는다. 기본 타입으로 cast하면 데이터 요소(라벨 등) 연결이 끊길 수 있다.
