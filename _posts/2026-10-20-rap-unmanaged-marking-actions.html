파라미터 Abstract Entity

  • abap_boolean은 OData V4에서 Edm.Boolean으로 노출되어 JSON true/false로 주고받음
  • 필드 이름이 그대로 body 키가 되므로 소문자 zflag 그대로 보내야 함
  • 두 Action의 파라미터 구성이 같아서 AE 하나를 공유. 구성이 갈라지면 그때 분리
  • 테이블의 ZFLAG(출력 지시자)와 이름만 같은 별개라 헷갈리기 쉬움. 중립 이름(예: setvalue)을 권장
2

BDEF 선언

  • internal update;로 핸들러 내부 MODIFY만 허용하고 외부 PATCH는 차단
  • MarkDelete는 result [1] $self로 갱신된 행 1건을 반환
  • MarkPrint는 별도 결과 구조를 [0..*]로 반환해 응답 모양을 비교
  • BDEF를 먼저 활성화하고 클래스를 나중에 활성화
3

로컬 버퍼와 핸들러 정의

  • unmanaged는 update(버퍼) → read(버퍼 덮어쓰기) → save(DB)를 직접 구현
  • mt_upd의 c_del / c_flag는 그 컬럼을 이번에 바꿨는지 기억해 다른 지시자를 덮어쓰지 않게 함
  • update 메서드를 핸들러에 선언해야 BDEF의 internal update와 짝이 맞음
4

Action 핸들러: MarkDelete / MarkPrint

  • 두 핸들러의 차이는 건드리는 컬럼(zdelete vs zflag)과 result 조립 방식뿐
  • 핸들러에서 UPDATE를 직접 치지 않고 MODIFY ENTITIES로 RAP 흐름(버퍼 → save)을 탐
  • failed를 채우면 save가 스킵되어 성공 건까지 같이 날아감. 부분 성공이 필요하면 비워둠
5

update / read 핸들러

  • update는 DB를 건드리지 않고 버퍼에만 쌓음
  • %control은 'X'가 아니라 if_abap_behv=>mk-on과 비교
  • read가 비어 있으면 instance action 호출이 안 됨. MODIFY 직후 READ에 방금 찍은 값이 보이게 버퍼를 덮어씀
  • 엔티티 쪽 필드명은 CDS 뷰의 alias 기준. 가정하지 말고 실제 alias 확인
6

Saver: 진짜 UPDATE

  • DB UPDATE는 save 안에서만 수행
  • 관리 필드(local_last_changed_*)는 unmanaged라서 직접 채움
  • cleanup에서 lcl_buffer=>clear( )로 두 버퍼를 함께 비움
  • ImpData insert 시 created_by / created_at은 아직 채우지 않음 (다음 정리 항목)
7

호출 테스트

  • 대상 행은 body가 아니라 URL의 키로 지정. GUID는 하이픈 있는 8-4-4-4-12 형식
  • body는 BDEF에 선언한 파라미터 zflag 하나만. 엔티티 컬럼(Zdelete)을 넣으면 안 됨
  • boolean은 문자열 "X"가 아니라 JSON true/false
  • Bruno의 Body 모드는 JSON, Content-Type: application/json 확인

AE 재사용과 EDM 이름 충돌

  • "AE 재사용 금지"가 아니라 확인된 충돌은 한 가지 조합
  • yhl2609a001rt가 ImpData deep result의 자식이자 MarkPrint의 단독 result여서 충돌 → ya_yhl2609_0001_return으로 분리해 해결
  • "내부 이름이 달라서 두 번 만들어진다"는 에러 스택에서 추론한 설명이며 문서로 확인한 것은 아님
  • 실무 원칙: action 그룹마다 result AE를 따로 둠
상황판단
AE를 deep 구조의 자식으로 쓰고, 다른 Action의 단독 result로도 씀충돌 확인됨. AE를 분리
AE를 여러 Action의 단독 result/parameter로만 씀보통 괜찮을 것으로 보지만 이 환경에서 검증 안 됨
deep 구조끼리 같은 AE를 자식으로 공유해본 적 없음. 안전하게 분리

다음 단계: 일괄 마킹 설계 (미검증)

  • 아직 구현하지 않은 설계. 호출자가 키 목록을 갖고 건별 결과를 받는 static action + deep parameter 방식
  • 처리 흐름: 키 일괄 조회(for all entries) → 건별 검증(빈 키/없는 키/중복 키는 결과에 E) → 합격 건만 MODIFY ... update from → failed는 비워 부분 성공 유지
  • 구현 시 확인: _items 이름은 추정이라 $metadata로 확인, %cid 에러 시 [0..1] deep result로 전환, 결과 AE 충돌 시 bulk 전용 AE로 분리
