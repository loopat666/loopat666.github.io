SBOOK 대량 데이터 aRFC 병렬 처리

SBOOK 을 날짜 범위로 조회해 청크로 나누고, 가용 Work Process 수에 맞춰 aRFC 로 병렬 처리합니다. 실패한 청크는 대기 · 재시도 후 순차 재처리까지 이어집니다.

개요

  • SBOOK 을 FLDATE 범위로 읽어 청크 단위로 나누고, 가용 Work Process 수에 맞춰 aRFC 로 병렬 처리하는 데모
  • 리포트(조회·출력) / 클래스(병렬 처리 캡슐화) / RFC FM(청크 처리) 3계층. 데이터 추출은 호출측, 처리는 클래스가 담당
  • 개발 순서: FM → 클래스 → 리포트 → 소요 시간 측정 → 청크 크기 튜닝 → 막혔던 지점 정리
  • 문법 기준: ABAP 7.54+ · S/4HANA On-Premise (인라인 선언, VALUE #( ), REDUCE, += 사용)

RFC Function Module

  • Remote-Enabled Module 이어야 aRFC(STARTING NEW TASK) 대상이 됨. 파라미터는 모두 Pass by Value
  • IT_SBOOK 은 청크 1개, 반환은 EV_COUNT / EV_CANCELLED. 클래스 콜백이 같은 이름으로 RECEIVE 하므로 파라미터명을 바꾸면 클래스도 수정해야 함
  • 건별 처리 로직은 TODO 자리에 작성. DB 변경이 있으면 FM 안에서 COMMIT WORK (각 태스크는 독립 LUW)
  • 시스템 등록명 기준으로 정리 (최초 제공본은 Z_SBOOK_PROCESS_CHUNK / ZTT_SBOOK)
2

병렬 처리 클래스

  • 생성자 파라미터로 FM 이름 · 청크 크기 · 병렬 수를 받음 (기본값 ZFM_2609_SBOOK_PROCESS_CHUNK / 500 / 5)
  • run 흐름: 상태 초기화 → init_resource → 청크 분할 · dispatch → WAIT UNTIL mv_running = 0 → retry_failed
  • 동시 실행 수는 WAIT UNTIL mv_running < mv_max_tasks 로 제한. resource_failure 시 내 태스크 종료를 기다리거나 3초 대기 후 최대 20회 재시도
  • 실행 중 청크는 mt_inflight 에 보관 → 실패하면 mt_failed → 마지막에 현재 세션에서 순차 재처리
  • DB 커서는 사용하지 않음. 전부 SELECT INTO TABLE 로 읽은 뒤 메모리에서 분할 (WP 전환 시 커서가 닫히는 문제 회피)

리포트 · 실행

  • 데이터 추출은 리포트 책임. lt_all 을 TY_BOOKINGS 로 선언해 청크 · FM 파라미터와 타입을 맞춤
  • SELECT 는 커서 없이 INTO TABLE. 0건이면 메시지 후 종료
  • 출력은 get_result( )(태스크별) + get_summary( )(집계). R / E 행의 msg 로 실패 원인을 확인

소요 시간 측정

  • GET TIME STAMP + cl_abap_tstmp=>subtract 사용. GET RUN TIME 은 i 형(마이크로초)이라 약 35분을 넘기면 오버플로우가 나서 대량 처리에는 부적합
  • 클래스만 수정하면 되고 리포트는 그대로. get_summary( ) 결과에 elapsed_sec 이 함께 출력됨
  • 측정 범위는 run 전체. SELECT 시간까지 보려면 리포트에서 select 앞뒤로 같은 방식으로 따로 측정
  • VALUE #( ) 의 필드 목록은 쉼표 없이 줄만 추가

1. ty_summary 에 필드 추가 (PUBLIC SECTION)

2. 시작 / 종료 시각 attribute 추가 (PRIVATE SECTION)

3. run 의 시작과 끝에서 시각 기록

4. get_summary 에서 경과 시간 계산

청크 크기 튜닝

  • 500건 × WP 5개 는 "태스크당 500건 · 동시 5개". 500건 패키지를 5개 WP 가 100건씩 나눠 처리하는 의도라면 iv_chunk_size = 100
  • 채택안(A): 고정 크기 청크를 던지고, 끝난 WP 가 다음 청크를 바로 수령 → 5개 WP 가 계속 가동. 코드 변경 없이 호출부 값만 변경
  • 비채택안(B): 500건 패키지를 5등분하고 패키지마다 전부 끝나길 대기 → 가장 느린 태스크에 맞춰 나머지 WP 가 놂
  • 청크가 너무 작으면 aRFC 호출 · 콜백 오버헤드, 너무 크면 마지막 태스크만 남는 꼬리 현상과 재처리 비용 증가. elapsed_sec 로 100 / 250 / 500 을 직접 비교
  • 같은 전표 · 오브젝트를 건드리는 처리는 같은 청크로 묶어야 enqueue 충돌을 피할 수 있음
