데모 클래스 뼈대

  • if_oo_adt_classrun 을 구현해서 ADT에서 F9 로 바로 실행합니다 (결과는 Console 탭)
  • 줄 타입 ty_air 는 글자형 3개(carrid, carrname, currcode)와 숫자형 1개(seats). 이 구성이 DEFAULT KEY 실험의 핵심입니다
  • carrids 도우미는 ANY TABLE 로 받아서 어떤 종류의 테이블이든 carrid 만 뽑아 보여줍니다
  • 샘플 데이터는 KE 가 두 줄(300석 / 120석). 이 중복 한 줄이 선언마다 어떻게 처리되는지가 이 글의 관전 포인트입니다

DEFAULT KEY: 눈에 안 보이는 키

  • 키를 적지 않으면 숫자형·테이블·참조형을 뺀 나머지 필드 전부가 키가 됩니다. 여기서는 carrid + carrname + currcode
  • BY, COMPARING 없이 쓴 SORT 와 DELETE ADJACENT DUPLICATES 가 이 숨은 키를 그대로 사용합니다
  • 결과: seats 가 달라도 KE 두 줄이 중복으로 합쳐졌습니다 (4건 → 3건)
  • 편의점 재고표로 비유하면, 장부 어디에도 "키는 상품코드+상품명+통화"라고 적혀 있지 않은데 시스템이 몰래 그 기준으로 같은 줄을 판정하는 셈입니다
  • 필드를 하나 추가하면 키도 조용히 바뀝니다. 컴파일 에러 없이 결과만 달라지는 유형이라 가장 위험합니다

EMPTY KEY와 명시한 키

  • with empty key : 키가 없다고 선언합니다. 정렬·중복 기준은 SORT … BY, COMPARING 으로 직접 적습니다
  • 코드에 기준이 그대로 보이니 의도가 남습니다. ② 결과의 KE 좌석 120은 BY carrid seats 때문입니다
  • with non-unique key carrid : 키가 선언부에 보이고, 기준 없는 SORT · DELETE ADJACENT DUPLICATES 도 이 키로 동작합니다
  • ③ 의 KE 300은 STABLE 덕분입니다. 같은 키는 원래 순서를 유지하므로 먼저 온 KE(300석)가 살아남습니다. STABLE 이 없으면 어느 KE가 남을지 보장되지 않습니다
  • standard 테이블은 키로 찾아도 내부는 처음부터 훑는 선형 탐색입니다
  • 키가 없는 테이블에는 BY 없는 SORT 를 쓰지 않습니다. 기준이 비어 있어 의도한 대로 동작하지 않습니다

SORTED · HASHED · table_line

  • sorted: 넣는 순간 자동 정렬되고 이진 탐색이 빠릅니다. 인덱스 접근도 됩니다. 대신 APPEND 로 순서가 깨지면 런타임 에러라서 INSERT … INTO TABLE 을 씁니다
  • hashed: 키로 바로 점프합니다. 인덱스("몇 번째")가 없고 LOOP 순서에도 의미를 두지 않습니다
  • 둘 다 unique 기본 키가 중복되면 INSERT 가 sy-subrc = 4 로 조용히 거절합니다 (④⑤의 KE)
  • table_line : 값 하나짜리 hashed 테이블은 중복 제거 + 존재 확인용 명단으로 딱 맞습니다. ⑥ 에서 KRW를 두 번 넣어도 1건만 남습니다
  • 리터럴을 직접 INSERT 할 때는 CONV s_currcode( 'KRW' ) 로 줄 타입에 맞춰야 합니다 (막혔던 지점 참고)

보조 키와 ANY TABLE 파라미터

  • 기본 키는 비우고 보조 키 by_carrid(unique hashed)만 추가했습니다. 입력 순서(KE, AA, LH)는 그대로 두고 carrid 검색만 빠르게 만드는 구성입니다
  • unique 보조 키 위반은 sy-subrc = 4 가 아니라 예외입니다. 안 잡으면 덤프가 나므로 line_exists( lt[ KEY by_carrid … ] ) 로 미리 확인합니다 (⑦ 의 거절 KE)
  • 생략형 type table of x 는 standard + default key 와 같습니다. 키를 안 적은 줄이 사실은 ① 이었던 셈입니다
  • 파라미터를 ANY TABLE 로 받으면 키가 달라도 다 받습니다. TYPE tt_empty 로 받았다면 default key 테이블을 넘기는 순간 활성화 에러가 납니다

장단점 비교와 선택 가이드

  • 한 줄 요약: 키를 쓸 거면 보이게 적고, 안 쓸 거면 없다고 적자. DEFAULT KEY는 그 중간의 "숨은 키"라서 새 코드에서는 피합니다
  • 용도로 고르면 쉽습니다. 담기만 하면 EMPTY KEY, 찾기·확인이면 SORTED/HASHED, 정렬·중복 제거를 한다면 키를 명시

장단점 비교

선언장점단점 · 주의이럴 때
① DEFAULT KEY키를 안 적어도 SORT, COLLECT 가 돌아감. 옛 코드와 호환키가 숨어 있음. 필드를 추가하면 키가 조용히 바뀜. 숫자 필드만 있으면 키가 텅 빔옛 코드와 타입을 맞춰야 할 때만
② EMPTY KEY의도가 명확. 필드를 추가해도 안 바뀜. VALUE, FOR, CORRESPONDING 같은 현대 문법과 궁합이 좋음정렬·중복 기준을 매번 직접 적어야 함. 키 조회는 선형 탐색담아서 넘기기만 하는 응답, 버퍼, 로그
③ 명시한 키 (standard)키가 선언부에 보임. 기준 없는 SORT, DELETE ADJACENT 가 안전키 조회는 여전히 선형 탐색. 같은 키의 순서는 STABLE 이 있어야 보장정렬·중복 제거를 자주 하는 목록
④ SORTED항상 정렬. 이진 탐색이 빠르고 인덱스 접근도 됨. 부분 키로도 빠르게 찾음넣을 때마다 정렬 비용. APPEND 주의. 키 필드 수정 불가정렬이 필요하면서 자주 찾는 목록
⑤ HASHED건수와 무관하게 조회가 빠름. unique로 중복을 막아줌인덱스 접근 불가. 순서 없음. 키 전체 일치로만 빠름수천 건 이상의 존재 확인 · 조회
⑥ table_line hashed중복 제거와 존재 확인이 코드 몇 줄로 끝남값 하나짜리만 해당코드 목록 (통화, 항공사 코드 명단)
⑦ 보조 키순서를 유지하면서 여러 방식으로 빠르게 검색선언이 길어지고 키 유지 비용이 듦. unique 보조 키는 위반 시 예외라 사전 확인 필요한 테이블을 서로 다른 키로 자주 찾을 때
⑧ ANY TABLE 파라미터키·종류와 상관없이 받음필드 접근은 ASSIGN COMPONENT 같은 동적 방식범용 도우미 메서드
