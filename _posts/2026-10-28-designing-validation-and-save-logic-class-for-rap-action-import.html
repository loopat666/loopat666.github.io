  • BIMPL 핸들러는 얇게, 검증·버퍼·저장은 순수 ABAP 클래스로 위임 (action 단계에서 recv_data, saver 단계에서 save)

출발점: v1 진단

  • v1은 버퍼에 먼저 넣고 나중에 검증하는 구조. 택배를 창고 선반에 다 꽂아놓고 검수하는 꼴이라, 불량이 나오면 "몇 번 칸이었지?" 계산이 필요함
  • 그 계산이 iv_from, lv_buf_from, lv_log_from, lv_buf_from + lv_in - 1 같은 인덱스 산수로 퍼져 있음
  • "이미 수신 = 에러" 규칙인데도 기존 레코드의 airline_key, created_by/at를 조회해서 들고 다님 (입장 금지 회원의 회원카드 번호를 챙기는 꼴)
  • 로그를 'N'(미판정)으로 먼저 쓰고 결과가 나오면 다시 덮어씀 (이름 먼저 쓰고 채점 후 지우개질)
증상원인개선 방향
인덱스 변환 계산이 메서드마다 반복검증 대상이 누적 버퍼(mt_buffer)라 이번 호출분 범위를 계속 계산해야 함로컬 테이블로 먼저 검증 → 행 번호 = 로그 seq
죽은 코드 (lt_exist, 키 재사용, created_at 분기)기존 레코드는 항상 에러인데 update 경로를 남겨둠check_exists 검증 규칙으로 독립, 저장은 INSERT
로그 2회 기록 + 220자 수동 체크결과 판정 전에 로그부터 적재결과가 다 나온 뒤 한 번에 기록, bapi_msg 대입 시 자동 절단 활용
통화 캐시·증분 중복추적LUW 전체 최적화를 위한 상태 관리호출마다 1회 SELECT, COLLECT로 개수 세기

AON: 현관에서 검수하기

  • 핵심 발상: 검수를 창고 안이 아니라 현관에서. 들어온 데이터를 로컬 테이블 lt_rows로 먼저 검증하고, 통과했을 때만 mt_buffer에 적재
  • 한 LUW 안에서 recv_data가 여러 번 불려도, 한 번이라도 에러면 fail( )로 버퍼를 비우고 이후 호출도 전부 취소 (한 명 지각하면 반 전체 소풍 취소)
  • 에러는 (seq, text) 쌍의 sorted table 하나로 통일. 검증 규칙은 메서드 하나씩, validate에 한 줄 추가로 확장
  • save_main은 check mt_buffer is not initial 하나로 충분 (fail( )이 버퍼를 비우니까)

PARTIAL: 에러건만 skip

  • AON 뼈대(현관 검수)를 그대로 쓰고, 버퍼에 넣는 단위만 요청 전체 → 행 하나로 내림 (지각생만 두고 버스 출발)
  • mv_failed, fail( ), "전체 취소" 메시지가 전부 사라짐. 에러 없는 행만 키 채번 후 버퍼 적재
  • 리턴은 요약 1줄(전부 성공 S / 일부 성공 W / 전부 실패 E) + 행마다 1줄씩 성공·실패 전부
  • 같은 요청 안의 중복 carrid는 어느 쪽이 진짜인지 모르니 둘 다 에러, 같은 LUW 앞선 호출에서 이미 접수된 건은 먼저 온 쪽이 이김

BP 클래스에서 호출하기

  • action 핸들러(lhc_Airlines)와 saver(lsc_ZR_YHL2609_0020)는 서로 다른 인스턴스라 인스턴스 변수로는 데이터를 넘길 수 없음. 그래서 lcl_buffer의 class-data에 로직 클래스를 보관 (action에서 물품보관함에 맡기고 saver에서 찾아가는 구조)
  • get( )은 없으면 만들고 있으면 그대로 돌려주는 lazy 생성, clear( )는 인스턴스째 버려서 mt_buffer·mt_log를 한 번에 정리
  • AON ↔ PARTIAL 전환은 주석 처리된 4곳(get 리턴 타입, go_logic, lt_data 타입, corresponding)만 바꾸면 됨. 두 클래스의 public 시그니처가 같아서 가능한 일
단계메서드하는 일
InteractionImportDatakeys의 %param-data를 모아 recv_data에 위임하고, 리턴 메시지를 action result([0..1], 안에 메시지 N줄)로 변환
Savecheck_before_save현재는 바로 return. 주석 처리된 안전망 코드는 이전 설계(validate_data)의 흔적이라 지금 클래스와는 맞지 않음
Savesavelcl_buffer=>get( )->save( ) 한 줄. 본 데이터 INSERT → 로그 저장, COMMIT WORK는 프레임워크 몫
Savecleanuplcl_buffer=>clear( )로 인스턴스 폐기 → 다음 요청은 깨끗한 상태에서 시작
포인트설명
BIMPL은 얇게핸들러는 "변환 → 위임 → 결과 포장"만 하고, 검증·버퍼·저장 판단은 전부 로직 클래스가 담당. 로직을 바꿔도 BIMPL은 그대로
에러를 failed에 안 넣는 이유검증 에러를 failed/reported로 올리면 changeset 전체가 롤백됨. PARTIAL의 성공건까지 날아가므로 에러는 result의 mtype으로만 전달
check_before_save 안전망PARTIAL에서 여기서 failed를 채우면 위와 같은 이유로 전체 롤백. 되살린다면 AON 전용으로만 사용

이름 체계와 선택 기준

  • v1, v2, v3 같은 버전 번호 대신 동작 방식을 이름에 박는 체계로 변경. 6개월 뒤에 봐도 이름만으로 성격이 보임
  • 클래스는 ADT에서 Rename이 애매하므로, 새 이름으로 생성 → BIMPL 호출부 교체 → 활성화 확인 → 이전 클래스 삭제 순서로 진행
클래스성격어울리는 상황
ZCL_2609_AIRLINE_AONAll-or-Nothing건끼리 연관이 있어 일부만 들어가면 데이터가 어긋나는 경우, 송신측이 "전부 재전송"으로 재처리하는 경우
ZCL_2609_AIRLINE_PARTIAL부분 저장건끼리 독립적인 마스터 데이터, 송신측이 실패건만 골라 재전송할 수 있는 경우
