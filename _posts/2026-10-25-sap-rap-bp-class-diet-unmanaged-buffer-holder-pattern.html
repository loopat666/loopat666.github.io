RAP Unmanaged 수신 API의 버퍼 홀더 패턴

RAP Unmanaged 시나리오에서 static action으로 데이터를 수신하고, 검증·저장·로그를 로직 클래스에 위임해 BP를 얇게 유지하면서, 에러 시 요청 전체를 저장하지 않는(all-or-nothing) 대량 수신 구조를 구현한 과정을 정리했습니다.

개요

  • RAP Unmanaged 시나리오에서 static action ImportData로 항공사 데이터를 수신·검증·저장하는 연습용 API (테이블 yhl2609t0020)
  • BP는 얇게: 상세 로직은 로직 클래스 zcl_2609_airline_v1에 두고, 인스턴스는 BP 로컬 클래스 lcl_buffer가 보유하는 버퍼 홀더 패턴
  • 한 건이라도 에러면 요청 전체를 저장하지 않는 all-or-nothing, 들어온 데이터는 성공/에러와 무관하게 로그 버퍼에 먼저 적재
  • 개발 순서: 테이블·CDS → 입출력 AE → BDEF → 로직 클래스 → BP → 호출 테스트
  • 편의점 택배 접수로 비유: BP는 접수 알바, 로직 클래스는 검수·발송 담당, lcl_buffer는 카운터 옆 바구니 (요청이 끝나면 바구니째 비움)

  2. 서비스OData V4 static action
  3. BP 클래스lcl_buffer로 위임만

1

테이블 · CDS

  • 키는 두 개: airline_key(UUID, 서버가 발급)와 carrid(업무 키). 호출자는 carrid만 보내고, UUID는 서버가 붙임 (UUID는 주민번호, carrid는 사번 같은 관계)
  • 관리 필드 4종(created_*, last_changed_*)은 unmanaged에서 프레임워크가 채워주지 않으므로 로직 클래스의 save에서 직접 세팅
  • CDS에는 @Semantics로 필드 의미를 선언, 필드 alias는 Carrid, Carrname 형태
2

입출력 Abstract Entity

  • 입력은 deep 구조: 루트 za_yhl2609_0020I 아래 composition DATA에 항공사가 N건 들어옴
  • 결과도 deep 구조: 루트 za_yhl2609_0021 아래 composition result에 메시지가 N줄 → 에러가 여러 건이어도 건건이 돌려줄 수 있음
  • 입력 AE에 airline_key를 넣지 않음: 호출자가 남의 UUID를 보내 기존 레코드를 덮어쓰는 길을 막고, 키 발급은 서버가 전담
  • AE 필드를 통화 같은 데이터 엘리먼트로 선언하면 프레임워크가 역직렬화 단계에서 값을 검사해 400이 먼저 나옴 (막혔던 지점 참고)
3

Behavior Definition

  • create, update, delete는 주석 처리: 외부에서 항공사를 직접 만들지 않고 ImportData 하나로만 수신하므로 해당 핸들러가 필요 없음
  • authorization master ( global )를 선언했으니 BP에 get_global_authorizations 메서드(빈 메서드)가 반드시 있어야 함, lock master용 lock과 read도 빈 껍데기로 둠
  • ImportData는 static action이라 키 없이 호출, 입력과 결과 모두 deep
  • etag master LastChangedAt은 update를 열 때 의미가 생김 (지금은 미리 걸어둔 상태)
4

로직 클래스 (zcl_2609_airline_v1)

  • BP는 호출만 하고 상세 로직은 이 클래스에 모음: 상태(mt_buffer, mt_log, mt_seen, mt_curr, mv_has_error)는 인스턴스 속성이라 싱글턴이 필요 없음
  • all-or-nothing: 에러가 하나라도 있으면 set_failed가 버퍼 전체를 비우고 mv_has_error를 세움 → 같은 요청의 다른 호출은 버퍼에 넣지 않고 로그만 남김
  • save는 save_main(본 데이터) 뒤에 save_log(로그)를 항상 호출: 에러 요청이라 본 데이터가 없어도 로그는 저장되도록 CHECK를 save_main 안에 가둠
  • 이미 DB에 있는 carrid가 들어오면 갱신하지 않고 에러(이미 수신되었습니다.) 처리, 신규와 섞여 있어도 요청 전체를 저장하지 않음
  • 수천 건 대량 수신을 가정한 구조 (원본과의 차이는 6단계 표 참고)

BP 클래스

  • lcl_buffer가 로직 클래스 인스턴스를 CLASS-DATA로 보유 (싱글턴이 아니라 BP가 소유): 핸들러와 saver가 같은 인스턴스를 봄
  • cleanup에서 lcl_buffer=>clear( )를 반드시 호출: 인스턴스째 버려서 버퍼·로그·플래그가 같이 초기화되며, 빠지면 다음 요청에 이전 데이터가 섞임
  • ImportData는 %param-data를 로직 클래스 입력 타입으로 변환해 recv_data에 넘기고, 결과를 result에 메시지 N줄로 감쌀 뿐
  • check_before_save는 비워둠: recv_data가 이미 이번 호출분을 검증하기 때문 (create/update를 열면 다시 살릴 것)
  • save 안에서 COMMIT WORK 금지: 프레임워크가 LUW를 소유

호출 테스트

  • 호출 순서: CSRF 토큰 확보 → ImportData POST (Bruno 등)
  • body의 루트 속성은 AE 이름 그대로 대문자 DATA, 속성명은 대소문자를 구분하므로 $metadata 기준으로 확인 (400이면 파라미터 이름부터 확인)

막혔던 지점 정리

증상원인해결
HTTP 400 /IWBEP/CM_V4_COS/170 Currency 'WON' does not exist (target: DATA-currcode), BP 메서드에 브레이크포인트가 안 걸림AE 필드가 통화 타입(s_currcode)이라 프레임워크가 JSON을 ABAP 구조로 바꾸는 단계에서 값을 검사함. 핸들러에 도달하기 전에 끊기므로 디버깅도 로그도 불가응답의 Timestamp/TransactionId로 /IWFND/ERROR_LOG(또는 ADT의 SAP Gateway Error Log) 확인, 통화코드는 KRW처럼 유효한 코드로 호출. 로그까지 남기려면 AE 필드를 일반 char로 바꾸는 방법이 있으나 보류
이미 저장된 데이터를 다시 보내면 또 처리됨 (save까지 감)기존 carrid면 UUID를 재사용해 같은 레코드를 갱신(upsert)하는 설계였음recv_data ③에서 기존 carrid를 에러(이미 수신되었습니다.)로 기록, 신규가 섞여 있어도 요청 전체 미저장
