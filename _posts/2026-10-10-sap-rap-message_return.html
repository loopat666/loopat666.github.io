failed vs reported 역할 구분

  • failed는 "누가, 어떤 작업에서, 어떤 종류(cause)로 실패했나"만 담아요. 메시지 텍스트는 못 실어요.
  • reported가 사용자에게 보이는 메시지(텍스트, severity)를 담아요.
  • 둘은 같은 키로 연결돼요. 한쪽만 채우면 반쪽짜리예요 (failed만 → 이유 모름, reported만 → 실패로 인식 안 됨).

reported키 + %msg(텍스트, severity) + 필드 표시O

코드 리뷰: 지뢰 정리

  • failed를 키 loop 밖에서 채우면 field symbol 해제 + 마지막 키 상태만 반영되는 문제가 있어요.
  • 공용 버퍼를 clear하면 다른 키의 정상 데이터까지 날아가요.
  • 에러 시 failed와 result(ret_type=E)를 같이 쓰면 방식이 섞여요 (failed가 있으면 4xx 에러 응답으로 끝남).
심각도문제해결
높음failed가 loop 밖, <ls_key> 사용키 loop 안, 에러 판단 직후에 채우기
높음공용 버퍼 전체 clear키별 임시 테이블에 모았다가 성공 시에만 버퍼로 이동
중간failed + result(E) 혼용전체 취소(A)와 비즈니스 결과 응답(B) 중 하나로 통일
중간lv_msg 덮어쓰기reported에 전부 쌓이니 A방식이면 OK, B방식이면 누적 필요
낮음sy-tabix 신뢰직접 카운터(lv_idx) 사용
낮음%action-ImpData 누락reported/failed에 mk-on 지정

전체 취소 방식 구현 (정책 A)

  • 정책 A: 키 하나라도 실패하면 그 키는 failed 처리하고 result는 채우지 않아요.
  • 검증은 끝까지 돌려서 에러 메시지를 전부 모아 주고, 적재는 임시 테이블 lt_new에만 해요.
  • 에러가 없을 때만 공용 버퍼로 옮기므로 롤백 코드가 필요 없어요.
  • failed가 있으면 RAP가 save를 건너뛰고 cleanup을 호출해요 (all-or-nothing).
4

reported 확장: 메시지 클래스, %other, severity

  • %action-ImpData = mk-on은 프레임워크용 내부 꼬리표라 응답 JSON에는 안 나와요.
  • action parameter 행 검증에는 %element를 쓸 수 없어요. "몇 번째 아이템"을 텍스트에 넣는 방식이 맞아요.
  • 추천 3종 세트: 메시지 클래스(코드 분리) + %other 요약 + severity 구분.

일부 성공 / 일부 실패 정책 (정책 B)

  • failed를 채우는 순간 요청 전체가 에러로 끝나고 롤백돼요. 부분 성공이면 일부러 failed를 비워야 해요.
  • 제외된 아이템은 warning으로 reported, 결과는 result에 S/P/E와 건수로 담아요.
  • 재전송 시 이미 들어간 건이 또 들어가므로 중복 방지(비즈니스 키 체크)가 필요해요. 지금 zlogkey는 매번 새 UUID라 방지가 안 돼요.
정책failedreportedresult
A. 전체 취소채움error채우지 않음
B. 부분 성공비움warning채움 (S/P/E + 건수)
C. 전체 취소 + 상세 리포트채움error (상세)채우지 않음

Postman으로 severity별 동작(warning이 에러로 처리되지 않는지)을 릴리즈에서 꼭 확인하세요.

에러 응답 해석과 추적

  • failed/reported로 낸 에러는 error.details 배열에 메시지별로 내려가고, 최상위 message는 대표 1건이에요.
  • 순서가 역순(180 → 1)이라 순서에 의존하지 말고 메시지 텍스트에 인덱스를 넣으세요.
  • innererror는 Gateway가 자동으로 붙이는 추적 정보예요. 형이 만든 비즈니스 에러와는 별개예요.

SABP_BEHV/100 벗어나기: 메시지 클래스 적용

  • SABP_BEHV/100은 new_message_with_text를 쓸 때 붙는 고정 코드예요. 메시지 생성 방식을 바꾸면 code가 ZMSG_FLIGHT/003처럼 바뀌어요.
  • 정석은 메시지 클래스 + 예외 클래스, 현실적인 타협은 메시지 클래스 + new_message예요. new_message_with_text는 임시용이에요.
  • 두 방식 모두 응답 code는 똑같이 나와요. 차이는 코드를 유지보수하는 쪽에 있어요.

방식 1. new_message + 메시지 클래스

  • 장점은 간단하고 빠르다는 거예요.
  • 단점은 'ZMSG_FLIGHT', '003' 문자열이 곳곳에 흩어져 오타를 컴파일러가 못 잡는다는 거예요.
  • v1~v4는 각각 최대 50자까지 들어가요.

방식 2. 예외 클래스 + 메시지 클래스

  • 심각도는 severity = if_abap_behv_message=>severity-warning만 추가하면 바뀌어요 (부분 성공 정책에 활용).
  • if_t100_dyn_msg, m_severity 구성은 릴리즈별로 다를 수 있어요. 막히면 SAP 샘플 /DMO/CM_FLIGHT_MESSAGES의 constructor와 비교하세요.
  • attr에 적은 이름(IDX 등)과 DATA 속성 이름이 철자까지 같아야 변수가 채워져요. 틀리면 &1이 빈칸으로 나와요.
  • 메시지 클래스와 예외 클래스는 같은 transport에 넣어 운영으로 이송해야 해요.

추천 순서: 먼저 방식 1로 4개 메시지를 적용해서 응답 code가 바뀌는 걸 확인하고, 메시지가 늘거나 다른 BO와 공유하게 되면 방식 2로 올리세요. 두 방식 모두 메시지 클래스 문구 표가 공통 기반이라 버려지는 게 없어요. 이 코드는 실행 검증 전이니 Postman으로 code가 ZMSG_FLIGHT/003으로 나오는지 확인하세요.

막혔던 지점 정리

증상원인해결
에러 메시지는 뜨는데 데이터가 저장됨failed를 안 채움에러 키마다 failed + %cid 지정
failed는 있는데 메시지가 안 뜸reported의 %cid가 failed와 불일치같은 %cid 사용
어느 키가 실패했는지 마지막 키만 반영됨failed가 loop 밖, lv_err 매 키마다 리셋failed를 키 loop 안으로 이동
정상 키 데이터까지 사라짐공용 버퍼 전체 clear임시 테이블 → 성공 시 이동

다음에 할 일

  • 수정안 적용 (failed를 loop 안으로, 임시 테이블 방식) 후 메시지 클래스로 전환
