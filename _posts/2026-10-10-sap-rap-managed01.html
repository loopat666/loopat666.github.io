SAP RAP managed 시나리오 구현

Fiori 화면 없이 OData V4 Web API로 데이터를 받는 managed 시나리오를 만들었다. 테이블부터 단건 POST, 메시지 반환, 커스텀 Action 다건 수신까지 개발 순서대로 정리했다.

개요

  • Draft 없는 managed 시나리오다. UUID 키 채번과 관리 필드 5개를 프레임워크가 자동으로 채운다.
  • 단건은 create로 받고, 다건은 static action(deep parameter)으로 한 번에 받는다.
  • 개발 순서는 테이블, R 뷰, BDEF, behavior pool, 서비스 정의/바인딩, 호출 테스트다.

  4. 프레임워크 save채번, 관리 필드, 저장

1

테이블 설계

  • 키는 SYSUUID_X16 (RAW 16)이어야 numbering : managed가 동작한다. SMI_UUID, SYSUUID_C32 같은 CHAR 타입은 안 된다.
  • 관리 필드는 abp_* 계열 데이터 엘리먼트를 써야 자동 채움이 맞물린다.
  • API 전용이라 draft 테이블, total etag는 필요 없다. 관리 필드와 etag 필드는 선택 사항이다.
2

R 뷰 어노테이션

  • 관리 필드는 필드 이름이 아니라 @Semantics 어노테이션으로 프레임워크가 알아본다.
  • 어노테이션은 BDEF가 붙은 R 뷰에 달아야 한다. Projection 뷰에는 달지 않는다.
  • 한 필드에는 어노테이션 하나만 단다. localInstanceLastChangedAt은 etag용, lastChangedAt은 루트 전체 변경용이다.
3

BDEF 작성

  • strict ( 2 )에서는 루트에 lock master와 authorization master가 필요하다.
  • mapping for ... corresponding은 이름이 같은 필드(대소문자 무시)만 자동으로 짝짓는다. 언더스코어가 있는 관리 필드 5개는 직접 매핑해야 한다.
  • 매핑에서 빠진 필드는 DB에 저장되지 않는다. 컬럼을 추가할 때 같이 확인한다.
4

Behavior Pool과 서비스 노출

  • BDEF에서 Quick Fix(Ctrl+1)로 behavior pool 클래스를 만든다. authorization master ( global )이라 get_global_authorizations가 필요하고, 비워둬도 된다.
  • 서비스 바인딩은 UI 타입이 아니라 OData V4 - Web API로 만든다.
  • BDEF를 바꾸면 재활성화 후 서비스 바인딩을 Unpublish / Publish 한다.
5

POST 호출 테스트

  • POST 전에 GET으로 X-CSRF-Token: Fetch를 호출해 토큰과 세션 쿠키를 받는다.
  • body에는 Zlogkey와 관리 필드 5개를 넣지 않는다. $metadata에서 Core.Computed가 붙은 필드는 서버가 채운다.
  • 응답에 요청 body가 그대로 돌아오는 것은 정상이다. 요청에 없던 Zlogkey, CreatedBy 등이 채워졌는지를 확인한다.
  • PATCH, DELETE는 etag 때문에 If-Match 헤더가 필요하다. 테스트 때는 *를 쓸 수 있다.

6

SAP__Messages 채우기

  • SAP__Messages는 reported에 담은 메시지가 나오는 칸이다. 아무도 담지 않으면 []다.
  • 성공/정보 메시지는 reported만, 요청을 거부하려면 failed도 함께 채운다. reported에만 error를 넣으면 저장은 막히지 않는다.
  • numericSeverity는 1=성공, 2=정보, 3=경고, 4=오류다. 메시지가 응답 body에 실리는지 헤더에 실리는지는 환경에서 확인한다.
7

다건 처리: 커스텀 Action

  • 다건 수신 방법은 $batch, 커스텀 Action, Deep Create 세 가지다. 연동 API는 건별 결과를 설계할 수 있는 Action을 쓴다.
  • Action 안에서 직접 INSERT 하지 않고 MODIFY ENTITIES ... CREATE로 프레임워크를 통과시켜야 채번, 관리 필드, validation이 동작한다.
  • 입력/결과가 부모-자식(deep) 구조면 abstract entity에 key dummyKey를 두고, abstract BDEF로 association을 선언한다.
  • 한 건이 실패해도 나머지는 진행되는 부분 성공 구조다. 전부 성공 또는 전부 롤백이 필요하면 failed_tmp가 있을 때 failed를 채워 Action 전체를 거부한다.
  • Action 정의 문법과 결과 구조는 활성화 때 에러가 날 수 있다. 에러 메시지를 기준으로 보정한다.
