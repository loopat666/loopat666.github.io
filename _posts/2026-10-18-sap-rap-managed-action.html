개요

  • managed 시나리오에 internal create + static action ImpData를 얹어, 여러 건을 한 번에 받아 저장하는 수신 API
  • action이 deep parameter로 목록(_composition)을 받고, 구현부에서 EML MODIFY ENTITIES ... CREATE로 일괄 접수. INSERT와 번호 발급은 프레임워크가 처리
  • 개발 순서: Root View → BDEF → Behavior Pool → 서비스 노출 → 호출 테스트
  1. 호출자POST + JSON (_composition)
  2. 서비스static action ImpData
  3. ImpData 구현%cid / Erdat 세팅
  4. EML createLOCAL MODE, Zlogkey 자동 발급
  5. 결과mtype / message 요약 1건

1

Root View (CDS)

  • @Semantics 어노테이션을 달아야 managed가 생성자와 변경 시각을 자동으로 채워준다. 어노테이션이 없으면 readonly만 걸린 빈 컬럼이 된다
  • 관리 필드 5개는 필수가 아니다. etag master, with draft를 쓰거나 감사 이력이 필요할 때 사실상 필요해진다. 이 시나리오는 이력용으로 유지
  • cast( fltime as abap.int4 )는 테이블 타입과 다르면 mapping 단계에서 타입 불일치가 날 수 있으니 확인
2

Behavior Definition

  • strict(2)는 lock과 authorization 선언을 요구한다. 엔티티가 하나이고 instance 대상이 없으므로 authorization master ( global )
  • numbering : managed는 UUID(RAW16) 키에만 쓸 수 있다. 외부 create는 막고 내부(IN LOCAL MODE)에서만 허용하려고 internal create
  • CDS 필드는 CamelCase, 테이블은 snake_case라 이름이 다른 관리 필드만 mapping ... corresponding에 적는다. 이름이 같은 필드는 자동 매핑
3

Behavior Pool (구현 클래스)

  • authorization master ( global )를 선언했으면 get_global_authorizations를 반드시 구현. 없으면 런타임에 CX_RAP_HANDLER_NOT_IMPLEMENTED
  • %cid는 행마다 유니크해야 한다. { key-%cid }_{ sy-tabix }처럼 행 번호를 붙인다
  • Erdat은 payload에 값이 없으면 시스템 날짜로 채운다. CREATE FIELDS 목록에 Erdat이 있어야 값이 반영된다
  • COMMIT WORK는 쓰지 않는다. LUW는 RAP 프레임워크 소유라 BEHAVIOR_ILLEGAL_STATEMENT가 난다
4

서비스 노출 (SD / SB)

  • Service Definition에서 Root View를 expose한 뒤, Service Binding을 만들고 Publish
  • 이 문서는 API 호출 기준. 정확한 action 경로는 $metadata에서 ImpData를 검색해 복사하는 게 가장 안전
5

호출 테스트

  • 1건으로 먼저 입구(역직렬화)를 통과시킨 뒤 50건으로 확장하면 디버깅이 쉽다
  • JSON 키는 $metadata의 Property Name과 한 글자도 다르지 않게 맞춘다. OData V4는 대소문자를 구분하며, 무시하는 옵션은 없다
  • ERDAT은 payload에서 생략. 구현부가 채운다

2. 응답

  • 성공 응답 후에도 DB에는 save 단계에서 INSERT된다. ADT Data Preview로 YHL2609T0001의 건수, Erdat, CreatedBy를 확인
  • 같은 payload를 다시 보내면 Zlogkey가 UUID라 중복이 그대로 쌓인다. 중복 방지가 필요하면 CARRID + CONNID 사전 체크를 추가
