개요

  • 헤더 1건에 아이템 N건을 담은 JSON을 action 한 번으로 수신하는 OData V4 Web API
  • 핵심은 unmanaged BDEF의 static action에 deep parameter(abstract entity)를 붙이는 구조
  • 개발 순서는 아래 1~8단계, 활성화도 같은 순서를 따름
  1. ClientJSON 배열 POST
  2. Service BindingOData V4 Web API
  3. Handler ImpData검증 후 buffer 적재
  4. Saver saveINSERT YHL2609T0001
  5. Result건수, 타입, 메시지

Abstract entity: 입력과 결과

  • strict 모드에서 action의 parameter와 result 타입은 abstract entity만 가능
  • deep 구조는 root에 composition, 자식에 association to parent로 연결
  • ret_message는 abap.string(0)로 선언. 그냥 string은 타입 정보 오류
  • FLTIME은 abap.int4. S_FLTIME의 변환 exit SDURA는 OData V4에서 덤프 유발
3

Abstract BDEF

  • deep parameter를 쓰면 입력 abstract entity에도 BDEF가 필요. 없으면 "no behavior definition" 오류
  • root와 자식 모두 define behavior for 블록 필요, 연결은 association _composition
  • field ( suppress ) dummyKey로 입력 JSON에서 더미 키 숨김
4

Root view entity

  • unmanaged BDEF가 붙는 대상. 저장 테이블 yhl2609t0001 기반
  • cast( fltime as abap.int4 )로 SDURA 도메인 연결을 끊음
5

Behavior definition

  • static action이라 특정 레코드 키 없이 호출. URI는 Flights/…ImpData
  • parameter는 abstract root(yhl2609a001), result는 [0..1] 단건
  • create / update / delete는 열지 않음. 이 서비스는 action 전용
6

Behavior pool 클래스

  • handler(ImpData)는 검증과 buffer 적재만. DB에 직접 쓰지 않음
  • saver의 save에서 INSERT, cleanup에서 buffer 초기화
  • 검증 규칙: CARRID 또는 CONNID가 비었거나 CARRID = 'ZZ'면 ret_type = 'E', buffer 비움
  • 결과의 %cid는 필수. 요청과 결과를 잇는 연결 값
7

서비스 정의와 바인딩

  • Service Binding은 OData V4 - Web API 유형, 서비스 정의 YHL2609A001U_01, 버전 0001
  • 엔티티 이름을 Flights로 노출. URI의 Flights가 이 이름
  • 모델을 바꿨다면 Binding을 Unpublish 후 Publish
Binding 이름YHL2609A001U_01_API_V4
Binding 유형OData V4 - Web API
서비스 URL/sap/opu/odata4/sap/yhl2609a001u_01_api_v4/srvd_a2x/sap/yhl2609a001u_01/0001/

호출 테스트

  • 순서는 GET으로 CSRF 토큰과 쿠키 받기 → POST로 action 호출. 쿠키 없이 토큰만 보내면 403
  • body에는 _composition 배열만. 바인딩 대상 _it(Flights)은 URI가 대신함
  • property 이름은 메타데이터 대소문자 그대로. 다르면 "Property is invalid" 400
  • 저장 확인은 SE16N에서 YHL2609T0001 조회
